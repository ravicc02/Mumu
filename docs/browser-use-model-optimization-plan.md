# Browser Use 与模型执行优化方案

调研日期：2026 年 11 月 12 日，Asia/Shanghai。

交付范围：基于现有代码、真实头歌页面、隔离故障注入和已配置模型测试形成优化方案。本轮不修改业务执行器，不保存或评测真实实验代码，不把调研中的环境操作声明为作业完成。

## 1. 核心结论

两类场景应共用任务管理、浏览器、账号和日志底层，分别使用不同执行流程。不能给同一个浏览器 Agent 换一段提示词，就认为两类作业都已适配。

| 场景 | 模型的职责 | 程序的职责 | 完成依据 |
| --- | --- | --- | --- |
| 结构化题目 | 理解题目，返回带稳定编号的答案 | 提取、校验、填写、回读、暂存、提交核验 | 作答单元校验、暂存反馈和平台提交回执 |
| 网页代码实操 | 理解要求、生成受限修改、根据失败结果修正 | 读取文件、保存回读、自测、评测、反馈和逐关核验 | 真实文件、测试结果、关卡通过及课堂结果 |
| 远程桌面实操 | 观察截图、拆分动作、判断界面变化和产物 | 同一远端实例的截图、坐标、键盘、焦点与操作回执 | 远端实际产物、题目约束和平台评测回执 |

用户提出的两类业务，在执行器层至少需要三个路由：structured、code、desktop。Notebook、图形仿真和文件交付可以在能力明确后扩展；不应把它们误判为普通文本输入框。

当前最值得优先做的改动是：代码实验增加“自测／评测结果 → 失败分类 → 有限修复”的闭环；云桌面增加视觉观察和真实输入工具；模型按能力配置，不再根据模型名称同时决定协议、视觉和规划模式。

## 3. 现有实现审查

### 3.1 结构化链路已经存在，但有适用范围

agent_runner.py 的 _run_structured_chaoxing_quiz 只识别指定的学习通作业 URL。quiz_adapter.py 负责提取题目、构造 QuizAnswerSheet、填写和校验；填空按空位数、共用选项按子题组处理。它不是所有平台的通用结构化适配器。

当前提示词要求每个 unit_id 返回一次，但不能用提示词替代程序检查。建议对所有平台统一检查编号唯一性、缺失项、选项范围、答案数量、控件回读和暂存反馈。读取成功、写入成功、暂存成功及已提交必须分别记录。

### 3.2 头歌当前属于专用代码执行器

agent_runner.py 遇到 educoder 会直接进入 execute_experiment，随后返回，不会进入下方通用 Browser Use Agent。因此，单独修改通用答题 Agent 的提示词，不会改善现有头歌执行过程。

当前流程是：

~~~text
核验账号和作业开放状态
→ 打开实验 → 限制为 Java/JUnit → 读取当前关卡文件
→ 模型一次返回 CodePatch → 保存并回读
→ 未允许评测：停在当前关卡等待审核
→ 允许评测：等待当前关卡 status == 2
→ 处理下一关 → 回读整个课堂实验
~~~

目前已经有文件白名单、并发修改检查、保存回读、逐关通过和课堂结果双重核验。这些应保留。

主要缺口如下：

1. 模型只拿到当前描述和可编辑文件，未形成依赖文件、环境状态、失败反馈和计划组成的任务上下文。
2. 评测函数只轮询通过状态，最多等待 150 秒；没有提取明确的编译失败、断言失败和运行错误并反馈给模型。
3. CodePatch 的 summary 只是修改说明，不是计划、操作回执或完成凭证。
4. 未开启自动评测时只保存第一待处理关卡就返回，不能宣称整个实验已完成。
5. 实例声明和文件操作可复用，但 .java 限制与 Monaco 前置条件会挡住远程桌面等环境。
6. 现有 Browser Use 提示词专注题目和输入框，不包含实操产物、远端运行位置、失败修复及阶段验收。

### 3.3 模型配置存在职责混用

当前根据模型名称是否包含 deepseek，选择 DeepSeek 适配器，并同时设置 use_vision=False、flash_mode=True、较低的每步动作数。备用模型也共用主要任务配置。

本机实际安装 Browser Use 0.12.6。其 Agent 支持 enable_planning、extend_system_message、output_model_schema、use_thinking 和视觉配置；源码明确在 flash_mode=True 时关闭 enable_planning。也就是说，当前快速模式不仅缩短输出，还会让框架规划不可用。

该版本默认仅对特定模型名称启用坐标点击。只把 use_vision 改为 True，不保证 click 工具已经暴露坐标参数。需要在已验证的视觉模型和桌面执行器上显式启用坐标能力，或提供自己的受限 desktop 工具。

当前 requirements.txt 写 browser-use>=0.12。官方当前文档已进入新的 1.x/1.0 beta 路线，工具和浏览器接口存在变化。本次方案以本机 0.12.6 为实现基线；先锁定依赖并验证，再单独决定升级，不能直接照搬新版文档参数。

## 4. 统一任务契约与路由

### 4.1 先识别交付物，再识别界面

“有输入框”不能决定走结构化答题。应先确认任务要求是答案、可执行程序、远端目录、数据库状态、Notebook、仿真电路还是提交附件。

路由器先使用平台元数据、可见控件和环境能力，模型仅处理规则无法确定的部分。模型输出路由后，程序再次检查工具能力；缺少必要工具时不得让 Agent 硬试。

建议新增 TaskSpec，至少包括：

~~~json
{
  "task_type": "practical_desktop",
  "environment": {
    "kind": "remote_desktop_canvas",
    "instance_id": "runtime-bound-instance",
    "execution_location": "educoder_remote",
    "capabilities": ["observe", "pointer", "keyboard"]
  },
  "goals": [
    {"id": "g1", "description": "使用指定工具在远端完成克隆", "evidence": ["directory", "git_repository", "remote_url"]}
  ],
  "constraints": {
    "required_tool": "remote_vscode",
    "required_directory": "myproj",
    "preserve_existing_work": true,
    "reset_environment": false
  },
  "permissions": {"save": true, "self_test": false, "evaluate": false},
  "budget": {"max_actions": 40, "max_repair_rounds": 3}
}
~~~

以上数值为首轮实现建议，不是经过大样本验证的最优参数。远端实例编号由适配器绑定，不交给模型任意填写。具体路径以当前题目和实例实际返回为准。

### 4.2 两类场景的执行流程

~~~mermaid
flowchart LR
  A["读取题目、产物要求和环境"] --> B{"类型与能力检查"}
  B -->|"题目与固定控件"| C["提取结构 → 模型答案 → 写入回读 → 暂存"]
  B -->|"代码与运行环境"| D["计划 → 受限修改 → 自测或评测 → 失败修复"]
  B -->|"远程桌面"| E["截图观察 → 单个动作 → 等待回执 → 验证产物"]
  B -->|"缺素材或缺工具"| F["说明阻塞项并保留可恢复信息"]
  C --> G["独立核验权限、产物和平台回执"]
  D --> G
  E --> G
  G --> H{"是否具备最终通过回执"}
  H -->|"是"| I["已完成"]
  H -->|"产物就绪但待审核或评测"| J["待介入"]
~~~

### 4.3 结构化答题的优化

- 保持“提取一次、模型批量返回、程序批量写入”的主路径，不为每个输入框调用浏览器 Agent。
- 按响应预算分组，长答案单独控制大小；不是固定把几十个长答案塞进同一个输出上限。
- 采用 unit_id、subunit_id 和题目／控件指纹，避免重载、排序或部分提取后写错题。
- 提取不完整时先补采集；答案编号不完整或越界时不写入，最多对明确失败的单元修复一次。
- 将答案生成、控件填写、内容回读、暂存、平台回执分为独立步骤。最终状态由程序决定。
- 缺附件、素材或指定文件时保持未完成，不将简答文本当作材料交付。

## 5. 网页代码实操闭环

### 5.1 按关卡形成可恢复的工作单元

每关保存任务说明、允许编辑的文件、只读依赖、环境信息、原始文件指纹、成功条件与检查点。先读取当前状态；平台已通过的关卡直接跳过。

代码模型返回受限补丁或完整文件，程序执行白名单、格式和原文件版本检查。优先补丁以降低覆盖风险；使用完整文件时继续保留当前回读核验。包名、类名、依赖和脚手架只能在题目授权范围内修改。

JUnit 任务要求编写测试，所以不能简单禁止修改所有测试文件；应按任务中的可编辑区域与文件白名单限制。禁止修改的是未授权的隐藏评测器、评分逻辑和平台通过状态。

### 5.2 运行、反馈和修复

~~~text
读取和计划
→ 生成修改 → 校验与保存 → 回读一致
→ 已验证为非计分且已授权的自测
→ 收集退出码、编译错误、测试失败与日志
→ 归类具体原因 → 修改相关文件 → 再次运行
→ 产物就绪 → 按权限评测 → 关卡与课堂回读
~~~

自测入口的语义必须先探测，不能假设所有平台的“运行”都不计分。正式“评测”按提交处理；只在当前任务明确允许评测时执行。

建议每关最多 3 个修复回合。同样错误且产物没有变化，连续出现 2 次就重新规划或请求所缺信息，不再原样重试。命令应检查退出码与输出；网页代码执行器应提供等价的结构化运行结果。

评测需要区分：排队、运行中、编译失败、测试失败、通过、请求未确认、结果未知。前两类等待，明确失败可以在授权预算内修复；结果未知只能查询，不可再次点击评测。150 秒只是当前超时，不能把超时当成已确定失败或允许重交。

### 5.3 代码实操工具

| 工具 | 返回的证据 | 约束 |
| --- | --- | --- |
| read_task / read_status | 说明、当前关卡、提交范围 | 只访问当前任务 |
| list_files / read_file | 路径、内容、版本指纹 | 任务目录及只读依赖范围 |
| apply_patch / save_file | 差异、保存回读结果 | 编辑白名单与旧指纹匹配 |
| run_self_test | 状态、退出码、编译与断言错误 | 已验证支持且已授权 |

| request_help | 缺失项、当前状态和建议操作 | 不伪装为任务成功 |

工具名是建议接口，不表示当前已经实现。优先复用当前头歌客户端和 ExperimentRuntime，不让模型自行生成带认证信息的 HTTP 请求。

## 6. 远程桌面实操设计

### 6.1 Browser Use 管外层页面，桌面工具管内部画面

外层页面的登录、课程、关卡、环境启动和评测入口可以继续使用 DOM 工具。Canvas 内部的 VS Code、文件管理器和终端需要截图定位、坐标点击、双击、拖动、键盘组合键及输入确认。

本机 Browser Use 0.12.6 已有坐标点击能力，不必重写整个浏览器框架。软件也已有同一任务页面的截图流、view_id 和 CDP 输入分发，可以复用；还需要补齐模型可调用的工具封装、双击／拖动语义、画面版本检查和动作后验收。

不能把软件主机上的本地终端当成头歌远程终端。即便在本地成功创建 myproj，也不能证明头歌环境有该目录。remote.exec 只有在确有受支持的远端连接、实例身份验证和权限时才能提供；本轮没有验证到这样的接口，不在首版假设它存在。

题目若明确要求通过 VS Code 图形界面操作，应按指定路径完成，终端可用于允许的验证。不能因为文件结果看似相同就擅自绕过指定工具或替换题目仓库。

### 6.2 最小桌面工具集

| desktop.click / double_click | 当前帧编号、归一化坐标、按钮 | 只能点当前远端区域，拒绝过期帧与越界坐标 |
| desktop.drag | 当前帧和起止点 | 边界、时长和按键释放 |

| desktop.type_text | 文本、输入通道、预期焦点 | 确认远端焦点，选择已验证的键盘或粘贴通道 |
| desktop.wait | 当前目标的可观察变化 | 重新观察到菜单、窗口、命令输出或环境状态；有时间上限 |
| inspect_artifact | 指定目录或当前产物 | 读取该远端实例的可验证结果，不能用本地文件代替 |

前端展示缩放、浏览器 CSS 坐标、截图像素和 Canvas 内部尺寸需要显式换算。每次操作绑定观察帧和环境编号，窗口变化后重新定位，不把本次调研的 876 × 785 或某个屏幕坐标写死。

现有实时输入中 text 走 Input.insertText，key 走 Input.dispatchKeyEvent。Canvas 内的远程桌面不一定把文本插入事件当作键盘事件，必须单独验收中文、组合键和长文本通道。首轮可先保证 ASCII 命令与基本快捷键；输入失败不能悄悄落入网页评论框。

### 6.3 一次动作，一次观察

桌面模式建议每步只执行 1 个产生界面变化的动作。打开菜单、切换窗口、提交命令之后等待对应回执，再决定下一个动作。禁止一次让模型返回十几个坐标点击后盲目执行。

操作回执至少包含 action_id、环境编号、观察帧、目标、执行时间、前后画面和验证结果。已受理但回执延迟的动作保持 waiting，不自动重发。对评测、文件覆盖、Git 提交和其他不可简单重复的动作，必须先查询结果或读取产物。

### 6.4 图形实操的验收

以本次 Git 样本为例，应按当前题目实际要求确认目标目录、仓库来源、所用工具和运行位置。如果任务还要求修改、提交或运行示例，应分别加入验收项，不能只看到“克隆完成”提示就完成全部任务。

本地操作凭证与平台评测分开保存。目录存在和 Git 状态可支持“产物已就绪”，最终仍需当前关卡和课堂结果回读。原本已经通过的关卡应跳过，而不是通过再次评测制造“本次完成”的记录。

### 7.7 交给程序核验的结果结构

模型输出不要直接使用数据库任务状态。可以使用独立的候选结果：

~~~json
{
  "phase": "verifying_artifact",
  "artifact_ready": false,
  "verified_goal_ids": ["g1"],
  "remaining_goal_ids": ["g2"],
  "evidence_refs": ["action-12", "check-4"],
  "next_action": {"tool": "desktop.observe", "arguments": {}},
  "blocker": {"kind": "missing_capability", "detail": "缺少当前远端画面的输入工具"}
}
~~~

程序验证 next_action.tool 是否在实际工具枚举中、证据引用是否存在、环境是否一致。缺少证据时不能通过改成 artifact_ready=true 或 status=completed 绕过核验。

上面的动作候选结构用于业务监督或单步决策。Browser Use 的 output_model_schema 定义最终 done 结果，不是单步工具参数结构，也不能替代工具注册。最终 PracticeOutcome 应保存已验证目标、剩余项、产物和回执引用；单步动作仍由已注册工具和步骤回调处理。

当前单次模型复验已显示，即便输出能解析，步骤仍可能列出不可用工具，或把未来平台回执写成理所当然的结果。因此必须校验工具与证据，不能只校验 JSON 形状。

## 8. 模型与 Browser Use 配置

### 8.1 按角色和能力选择

| 角色 | 必需能力 | 建议起点 |
| --- | --- | --- |
| 结构化答题 | 正确的结构化输出、题型理解 | 保留本次已通过小样本测试的模型，进一步扩大题型样本 |
| 代码实现与修复 | 代码、错误归因、多文件约束、稳定结构输出 | 配置独立代码模型角色，不因名称含 flash 就强制关闭规划 |
| 桌面执行 | 图像理解、坐标定位、工具调用与多轮状态保持 | 使用真实视觉及工具探测通过的模型；当前配置未完成视觉验收 |
| 结果核验 | 产物规则和平台回执 | 程序为主，模型用于解释差异，不授予改任务状态的权力 |

一个模型可以承担多个角色，不要求一次引入多个付费服务。先在同一模型上按任务类型设置策略；确实缺少视觉或协议能力时，再让用户选择可用模型。备用模型必须满足同一角色的必要能力，不能把文本模型自动接到视觉任务。

框架的 use_thinking、enable_planning 与上游 reasoning_effort 是不同层的配置。前者影响 Agent 输出协议和规划，后者是否有效取决于上游模型及接口。不要把“用户选择高思考”和“框架允许规划”混为一谈，也不要求模型向前台返回隐藏思考过程。

模型设置建议扩展为角色映射，并保存 provider_protocol、supports_images、supports_tool_calls、structured_output_mode、reasoning_parameter_mode、context_budget 和探测时间。不能根据名称推断全部能力，也不能把“接口接受了参数”当成思考强度已生效。

### 8.2 当前 0.12.6 基线下的配置片段

下面是建议配置片段，依赖桌面工具、视觉模型和 PracticeOutcome 的实际实现，并非本轮已经启用：

~~~python
desktop_tools.set_coordinate_clicking(True)
agent = Agent(
    task=task_contract,
    llm=verified_visual_model,
    browser_session=the_same_task_session,
    tools=desktop_tools,
    use_vision=True,
    flash_mode=False,
    use_thinking=True,
    enable_planning=True,
    max_actions_per_step=1,
    max_failures=3,
    output_model_schema=PracticeOutcome,
    extend_system_message=practical_policy,
    use_judge=False,
)
~~~

关闭 use_judge 不代表没有核验，而是由业务验证器读取真正的产物与平台回执。独立模型审查可以后续增加，但不能取代平台事实。

结构化答题不需要启用上述完整 Agent。代码路径优先通过受限工具读写与运行；只有环境导航或控件无法直接适配时，才使用浏览器动作或桌面观察。

### 8.3 上下文与成本控制

保留固定任务约束、当前计划和产物检查点，重点传递当前文件及必要依赖、最新失败报告、最近几次动作和当前截图。避免每回合重复发送完整教材、长历史和整页 DOM。

长任务按关卡保存检查点，压缩历史时保留权限、未完成目标、当前环境编号和最近失败，不只保留“正在处理”。输出预算按文件规模分配；现有 8192 的输出上限不代表能够安全返回任意 12 个大型完整文件。

模型服务网络重试、Agent 工具重试、业务修复回合需要一个统一预算，避免三层各重试三次。记录实际请求数、耗时和服务可返回的用量；没有用量时显示未知。

## 9. 失败恢复和用户状态

### 9.1 遇阻后的处理矩阵

| 问题 | 自动处理 | 何时停止自动处理 |
| --- | --- | --- |
| DOM 或窗口发生变化 | 重读当前页面／截图并重新定位，不使用旧坐标 | 连续 2 次没有可验证变化 |
| 焦点错误、文本未确认 | 检查焦点和输入通道，先观察真实结果 | 输入目标不明、可能重复执行或通道不支持 |
| 明确编译／测试失败 | 将错误反馈给代码模型，最多 3 轮最小修复 | 同错重复且无进展、超预算或涉及未授权文件 |
| 模型结构输出失败 | 记录协议错误，按能力声明修复一次结构或切换已验证协议 | 仍不符合结构；不执行畸形工具参数 |
| 网络超时、429、暂时上游错误 | 仅对可安全重试请求执行有限退避，遵守服务返回的等待时间 | 超预算，或请求可能已产生提交副作用 |
| 评测已发出但无结果 | 按任务与请求编号查询 | 超查询期限后标结果未知，禁止重复评测 |
| 缺素材、工具或授权 | 明确缺失项并保存检查点 | 立即停止对应执行路径，不生成假产物 |
| 登录验证或交互授权 | 保留当前环境和明确操作入口 | 交由用户处理，回来后重新观察状态 |
| 远端环境回收／实例改变 | 保存已确认进度和原实例信息 | 未确认产物持久化时不自动重置或重做 |
| 用户手动暂停／停止 | 暂停不继续动作，停止取消后续操作 | 仅由用户恢复；关闭查看器不等于暂停任务 |

网络退避和工具恢复的具体时间需要压测，不在本轮把某个固定秒数声明为最佳策略。写入和评测先确认幂等性；模型重试不能自动导致工具重放。

### 9.2 复用用户约定的状态语义

| 前台状态 | 确定条件 |
| --- | --- |
| 中断，红 | 模型、上游、网络、浏览器或环境故障导致执行无法继续；包含评测结果未知并给出查询建议 |
| 未完成，红 | 必要产物不完整、缺素材／工具、格式不支持或修复预算耗尽 |
| 待介入，黄 | 产物已完成相应本地检查并已保存，但未允许或尚需人工审核、评测、提交；不声称平台已通过 |
| 已暂停，灰 | 用户主动暂停 |
| 已完成，绿 | 当前范围全部关卡通过，课堂结果和必要提交已独立确认 |

继续保留排队、运行中和用户停止等执行控制状态。实操的 planning、observing、executing、testing、repairing、verifying 是阶段，不应再造一套互相冲突的前台任务状态。

“缺桌面工具”和“已做完待审核”必须区分。模型的 needs_intervention 只能作为候选信息，不能未经规则映射就写入前台黄色待审核。对于需要用户授权才能继续的未完成任务，应记录 resumable、blocker_kind 和具体入口，避免把“需要帮忙”呈现成“已经做完”。

### 9.3 用户操作闭环

执行前显示识别出的环境和所选范围；执行时实时浏览器与动作记录来自同一远端实例。模型每步只输出简短的目标、动作和验证结果，不把隐藏思考过程展示给用户。

卡住时显示“缺什么、已完成什么、怎么继续”。保留当前窗口和检查点，用户接管后点击继续，执行器重新读取文件／画面／平台状态，不能从头覆盖。结束时给出产物、局部验证、平台回执和剩余项。

例如，面向用户显示“测试文件已保存，但缺少依赖，尚未评测”；完整堆栈、控件结构和响应信息写入设置对应的日志目录，不新增日志页面或诊断导出入口。

| P1：JUnit 闭环 | 文件上下文、运行结果、明确失败反馈和有限修复 | 受控编译失败可以修复；未知评测结果不重复提交；平台回执真实 |
| P2：远程桌面 | 视觉模型、observe／pointer／keyboard、焦点及等待工具、产物检查 | 同一环境完成指定桌面动作，输入不落错区域，缩放不点偏 |
| P3：复合实操 | 多关卡计划、持久化检查点、人工接管恢复、更多语言／Notebook | 恢复不覆盖用户改动，跨关卡依赖与最终课堂结果一致 |

优先完成 P0 与 P1，再进入 P2。当前模型的代码小样本已可用；Canvas 是明确的工具和视觉缺口，单改提示词不会消除它。

### 11.2 测试矩阵

| 范围 | 必测内容 |
| --- | --- |
| 结构化题目 | 单选、多选、判断、填空、简答、共用选项、组合子题；编号遗漏／重复、答案越界、富文本、部分已有答案 |
| 写入与保存 | 页面重载、控件变更、保存失败、回读不一致；不能只有答案卡颜色变化 |
| 代码实操 | 编译失败、断言失败、缺依赖、多文件、只读文件、人工并发修改、局部通过 |
| 评测 | 排队、明确失败、通过、网络断开、结果未知、课堂结果延迟、重复点击拦截 |
| 桌面 | Canvas、异步打开窗口、焦点丢失、画面缩放、双击、组合键、输入法、长文本、命令回显延迟 |
| 实例与恢复 | 环境倒计时回收、页面关闭与查看器关闭、同账号多任务、人工接管、进程重启 |
| 模型协议 | 工具调用、结构化输出、视觉、思考参数、截断、空输出、不可用工具、上下文长度 |
| 真实性 | 模型说完成但无产物、文件存在但测试失败、局部通过但课堂未通过、伪造证据引用 |

建议先建立确定性夹具，再在用户明确选定、允许测试的头歌实验上扩大样本。当前未授权的真实课堂不应用于故障制造。新增验收的硬门槛为：未授权写入／评测为 0、假完成为 0、未知提交盲目重试为 0。

成功率、平均模型请求数、Token、每关耗时、人工介入率和恢复成功率按任务类型分别统计。第一轮小样本不能给出可信的生产成功率；后续每类至少覆盖不同环境和失败分支，并进行重复运行后再确定指标。
