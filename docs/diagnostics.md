# 统一日志存储与维护规范

## 用户只提供 main.log

点击左下角头像，进入“系统设置 → 存储目录 → 今日日志”，打开日志目录。排查今天发生的问题时，直接提供 main.log，不需要选择任务、导出诊断包或寻找多个任务日志。

~~~text
logs/
  main.log       今日详细日志
  oldmain.log    历史归档日志
  diagnostics/  内部现场记录与归档控制信息
~~~

两个文件使用 UTF-8，按事件分块排版。每块以本地时间、级别、模块和事件码开头，后跟缩进的 JSON 数据。文本编辑器可以直接打开；历史问题按需要提供 oldmain.log。

主日志保留任务状态、识别与填写回执、模型和工具调用、保存与提交结果、重试和异常。成功的接口读取、画面连接开关和普通心跳不写入主日志。警告、错误、失败请求和用户操作仍保留。

每块保留 trace_id、sequence、phase、state、event_id、请求编号和耗时等已有字段。空的顶层占位字段省略，业务数据中的空答案、false 和 0 保留，用于判断填写失败。异常堆栈按行展开；完整源码位置和已采集的控件现场留在相应事件中。

~~~text
[2026-11-12T19:13:00+08:00] ERROR | executor | task.exception
{
  "level": "error",
  "component": "executor",
  "code": "task.exception",
  "message": "作答核验失败",
  "trace_id": "示例任务编号",
  "phase": "verifying",
  "data": {
    "unit_id": "q22:r2",
    "expected": "C",
    "actual": ""
  }
}
~~~

维护脚本使用 app.diagnostics.layout.iter_records 读取，兼容新分块格式和旧 JSONL。升级时按原事件时间和关联编号整理已有主日志；日志正文中的换行会转义，不会伪造新的事件标题。

## 自然日与归档规则

1. 使用应用所在电脑的本地自然日，不按 UTC 日期切割。记录同时保留带时区时间、本地时间和 local_date。
2. main.log 只存本地日期为今天的记录。跨天时，将原 main.log 内容追加到 oldmain.log，再创建新的 main.log。
3. oldmain.log 持续追加历史，不用昨天内容覆盖更早历史。
4. 应用整夜运行但没有新任务时，后台维护仍检查跨天。退出后隔天再启动，也先归档再写入。
5. 同一天重启不会清空 main.log。跨日任务在新日志里补入任务编号和运行环境，便于单独排查今天的步骤。
6. 迟到的旧日期记录直接进入 oldmain.log，不混进今天的主日志。
7. 不再因为达到旧的 4 MiB 或 5 MiB 阈值，把今天的内容拆到其他文件。main.log 按日期切割，不按大小切割。

归档使用跨进程写锁与暂存状态。中途退出后能够继续未完成归档，保留原有历史。文件被其他程序锁住或磁盘不可写时会报告存储异常并重试，不能为继续写日志而删除未知来源文件。

## 日志包含的详细信息

| 类别 | 内容 |
| --- | --- |
| 应用与启动 | 应用版本、依赖、构建指纹、系统和 Python、启动阶段及初始化异常 |
| 接口 | 方法、路径、HTTP 状态、请求关联编号、耗时及失败原因 |
| 任务 | 平台、任务类型、trace_id、执行会话、状态变化、人工操作和结果 |
| 模型与工具 | 已采集的请求阶段、结构化返回、工具动作、失败分类和异常堆栈 |
| 题型与控件 | 已采集的题目、作答单元、控件结构、预期值与实际值、写入和核验差异 |
| 网课 | 目录、章节和资源标识、媒体进度、阅读处理、重试、暂缓与平台复验 |
| 结果 | 保存、提交与评测的实际回执，已完成范围、阻塞项和待人工处理原因 |

题目和控件现场直接作为文本结构写入主日志，不要求维护者另找 JSON 才能理解已采集内容。截图二进制仍是内部附件，日志记录其事件、引用和相关现场信息；视觉排查需要图片时可另附截图。

沿用已有的单事件、单快照和超长字段上限。没有采集到的内容、超限省略或平台不可见的信息不会补造，因此日志不能保证还原第三方平台的全部动态状态。

## 维护者读取

先按本地时间、trace_id 和 task_kind 定位今天的问题，再检查事件 code、阶段、单元编号、动作回执和异常原因链。不要依赖前台简短文案判断具体错误。

| 事件 | 用途 |
| --- | --- |
| log.day_started / app.context | 当日运行环境与日志开始信息 |
| task.context | 当前任务、运行环境、模型配置和登录存储元数据 |
| task.exception / runtime.log | 完整异常链、堆栈、源码位置与标准运行日志 |
| diagnostics.evidence | 已采集的题型、控件、模型返回和网课资源现场 |
| task.summary / 任务事件 | 结果、状态、核验回执、剩余项与恢复操作 |
| legacy.* / imported_from | 兼容导入的旧日志及其来源 |

兼容导入保留原事件时间，追加顺序不一定等于原始发生顺序。需要重建时间线时按时间、执行会话和 sequence 排序；event_id 可用于识别恢复导入中的重复记录。

## 既有日志迁移与运行中任务

旧 backend.jsonl、backend.log 和既有任务日志会按原记录时间导入 main.log 或 oldmain.log。原文件兼容保留，不通过删除它们来伪装迁移成功。新版后端不再创建 backend.jsonl，也不再创建任务 task.log 分片。

新任务的详细记录直接进入 main.log。内部 events.jsonl、环境清单和现场 JSON 保留给程序兼容与任务恢复使用，但不是用户需要寻找或提供的主入口。

如果当前仍有旧后端在运行任务，可以使用本地兼容汇聚器持续收集其日志，不关闭任务、不操作浏览器。汇聚器绑定旧后端进程，后者退出后完成尾部导入并结束。之后新后端直接写主日志，不依赖汇聚器。

导入有持久化读取位置，正常重启不会重导全部记录。正在写入但尚未完成的一行会等待完成；损坏或受限内容保留来源说明，不当作有效平台操作回执。

## 脱敏和保留范围

写入前过滤 Cookie、Authorization、API Key、Token、密码和登录存储；旧日志迁移也使用已有配置和授权状态中的已知凭据做脱敏。保留必要的数量、名称、域和过期时间等元数据，不保存 Cookie 值。

日志仍包含排查所需的题目、答案和页面业务文本。不要用 .env、数据库或整个浏览器 Profile 替代主日志。

系统设置中的保留天数和空间上限只作用于内部任务现场记录。main.log 固定保留今天；oldmain.log 按本次规则累积历史，不被现场记录清理误删。

## 验证范围

自动测试覆盖同日重启、隔日启动、空闲跨日、连续多天归档、UTC 与本地日期差、迟到记录、大容量同日文件、线程及多进程并发、归档中断恢复、损坏状态保护和脱敏。

集成测试还验证独立后端启动写入 main.log，以及旧进程运行时在线汇聚、旧进程退出后尾部导入。所有测试使用隔离数据，不需要修改或提交真实作业。
